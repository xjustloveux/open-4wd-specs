## 重大重構里程碑

### 2026-11-23 ─ 重新檢舉的時戳須晚於既有案錄（issue 001494）

檢舉在撤回、流局或過期後可以重新檢舉，守門原本只看既有案錄的狀態、不比較時戳；已撤回或已流局的那筆檢舉事件
再次進入帳本時會被當成重新檢舉，以同一個案件 id 覆寫案錄，使撤回失效或留下無法結案的案錄。檢舉守門新增一個條件：
同一檢舉者對同一對象已有案錄時，新檢舉事件的時戳必須晚於該案錄的檢舉時戳，收件驗證與 fold 同一判定。
[程式架構/moderation.md](../程式架構/moderation.md)、[程式架構/ledger.md](../程式架構/ledger.md)、
[流程/檢舉與仲裁.md](../流程/檢舉與仲裁.md)、[信譽系統.md](../信譽系統.md) 同步。

> 決策檔：[D-20261123-01](../decisions/D-20261123-01-重新檢舉的時戳須晚於既有案錄.md)

### 2026-11-23 ─ 使用量與回饋金只計已有上傳紀錄的作品（issue 001468）

比賽結果事件引用的 UGC CID 原本只排除公版與本機前綴就進入使用量收集，帳本上沒有上傳紀錄的 CID 也會被記使用次數、
使用過的玩家與最近使用時間，作品日後上傳時名下已有先前累計的數字。收集規則新增一個條件：只收該事件 fold 位置
前態已有上傳紀錄的 CID；沒有紀錄的不計使用量、不發創作回饋金、不推進使用里程碑，上傳之後的比賽才開始累計。
不比對宣告的資產種類與配裝格位。[程式架構/ledger-settlement.md](../程式架構/ledger-settlement.md)、
[程式架構/economy.md](../程式架構/economy.md)、[程式架構/moderation.md](../程式架構/moderation.md)、
[程式架構/ugc-rating.md](../程式架構/ugc-rating.md)、[程式架構/reputation.md](../程式架構/reputation.md)、
[經濟系統.md](../經濟系統.md)、[信譽系統.md](../信譽系統.md)、[流程/比賽結算.md](../流程/比賽結算.md)、
[算式表.md](../算式表.md)、[UGC機制.md](../UGC機制.md) 同步。
[程式架構/ugc-rating.md](../程式架構/ugc-rating.md) 的 `canRate` 範例原本把「最近比賽中找得到引用該作品的場次」當成可評分，
與評分資格只讀使用量的判定不符，改寫為介面層的稽核欄補位說明：掃到的場次只用來填 `useMatchId`，不代表評分資格。

### 2026-11-23 ─ 帳本讀取以本機保留範圍為界、刪除全史讀取介面（issue 001502）

本機會淘汰已被 checkpoint 覆蓋的條目，但 event log 仍提供從 genesis 走到 heads 的全量走訪，啟動時的 checkpoint
公告掃描、定稿重試找既有公告、`getAllEvents` 與不帶參數的 `readEvents` 都用它；條目被淘汰後這些路徑會失敗，其中
啟動掃描失敗使帳本開不起來。log 的走訪改為從自己的淘汰邊界到 heads；啟動掃描讀這個範圍，定稿重試只讀本次
checkpoint 的 heads 到目前 heads；刪除 `getAllEvents`，`readEvents` 必須指定 checkpoint 且該 checkpoint 不在本機時
明確失敗；已有 checkpoint 而狀態塊讀不到時重建失敗，不退回 genesis 重放。
[程式架構/ledger.md](../程式架構/ledger.md)、[程式架構/ledger-checkpoint.md](../程式架構/ledger-checkpoint.md)、
[程式架構/interfaces.md](../程式架構/interfaces.md)、[程式架構/ugc-rating.md](../程式架構/ugc-rating.md) 同步。

文字更正（2026-11-24，行為未變）：被移除的是讀全部事件的專用入口，以空的起點呼叫區間走訪仍等於從 genesis 走訪，
已有 checkpoint 後不可靠；走訪起點不取 effective 指標的區別只存在於同一個 runtime 內，重啟時 log 的邊界就是以
effective checkpoint 的 heads 重建的；`readEvents` 指定較舊的 checkpoint 時會讀到邊界之前的條目，條目已被淘汰則
失敗；定稿重試找既有公告時，只有走訪以連續性錯誤拒絕才視為沒有既有公告，其他走訪失敗使定稿失敗；啟動掃描不保證
再讀到已被 checkpoint 涵蓋的同 previous sibling 公告。[程式架構/economy.md](../程式架構/economy.md) 中指向已刪除
介面的一句改為不依賴介面名稱的說法。

> 決策檔：[D-20261123-03](../decisions/D-20261123-03-帳本讀取以本機保留範圍為界.md)

### 2026-11-23 ─ 帳本 recovery 失敗後依退避重試（issue 001503）

增量折疊失敗後的全量重建若也失敗，原本沒有任何路徑會再試，節點只能關閉重開。改為在三種時機重試：失敗期間有
新條目到達、checkpoint 採納或定稿後的重建、退避計時器到期（1 秒、5 秒、30 秒、2 分鐘，之後固定 5 分鐘）；
任何一次成功的重建都清除失敗狀態並補發積欠的通知。啟動掃描在背景失敗改記為獨立狀態並自行重掃。另提供可讀的
復原狀態給介面顯示。[程式架構/ledger-checkpoint.md](../程式架構/ledger-checkpoint.md)、
[程式架構/ledger.md](../程式架構/ledger.md)、[程式架構/interfaces.md](../程式架構/interfaces.md)、
[程式參數/protocol.md](../程式參數/protocol.md) 同步。

文字更正（2026-11-24，行為未變）：三種時機並非共用同一個 single-flight 排程——新條目到達與退避計時器到期共用，
checkpoint 採納或定稿後的重建是另一個佇列工作，不經 single-flight、失敗不計入退避，三者都在狀態佇列中序列化；
ingest failure 期間到達的 checkpoint 公告目前不會被送進採納流程，採納後就不再成立的那類失敗只在公告於失敗前已
進入採納流程、或由啟動掃描送入時才等得到採納；復原狀態的次數是已失敗並排定重試的重建次數，進入失敗後立即執行的第一次重建也計入。

> 決策檔：[D-20261123-04](../decisions/D-20261123-04-帳本recovery失敗後依退避重試.md)
