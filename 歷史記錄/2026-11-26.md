### 2026-11-26 ─ 條目有效性改以檢查點切面與確定性時鐘判定（issue 001511、001522）

條目是否有效改由最新已採納檢查點的切面判定：每一個 parent 都必須在切面內，遠端 join 與本機提交同一規則，能否加入切面的判定不讀本機 index；
本機已有但不在切面與涵蓋範圍內的條目為孤兒，不在視圖、不能當 parent。條目時鐘必須恰等於 parent 最大值加 1（無 parent 為 1），
`clock.id` 必須等於簽章金鑰、簽章金鑰必須是條目 identity 的公鑰。開庫重建、涵蓋範圍還原與邊界推進套用同一規則，新增錯誤代碼
`stale-parent`、`clock-mismatch`、`covered-clock-mismatch`、`checkpoint-outside-cut`、`traversal-outside-cut`。被切面拒絕的本機寫入與
本執行期成為孤兒的自有條目，由寫入器以同一事件重新建立（每個意圖最多 3 次）。Orbit 寫入者身分改為每裝置、每鏈固定，存於該鏈
的 checkpoint control storage（損毀時 `ledger-orbit-id-corrupt`），簽署工具不再在資料目錄另存 id 檔。改寫 LEDGER-R-045、R-050，
新增 LEDGER-R-107、R-108、R-109。

### 2026-11-26 ─ 採納重試補做中斷的邊界推進（issue 001542）

遠端採納在寫入 latest 之後、邊界推進完成之前失敗時，重試原本因本體已是 latest 直接視為已採納，切面停在採納前。改為：本體就是
latest 且檢查點庫仍有指向它的待完成推進紀錄時，比照定稿路徑補做邊界推進、完成紀錄並以該檢查點重建；邊界推進或完成紀錄失敗回重試，
重建失敗不回重試、公告仍視為已採納，並依 LEDGER-R-048 進入 ingest failure、按退避重試。
[程式架構/ledger-checkpoint.md](../程式架構/ledger-checkpoint.md)（LEDGER-R-041）同步。

### 2026-11-26 ─ libp2p 節點加上 identify-push（issue 001553）

節點在連線之後才開帳本並登記 bitswap。identify 只在連線建立時執行，原本只有 identify，既有連線的對端要到重新連線才得知，
期間不會向本節點要內容塊。節點組態加上 `identifyPush()`，協定變更在去抖動之後推送給既有連線中支援推送協定的對端（本機實測
約 2 秒內通知）；瀏覽器端、簽署工具共用同一組態。
[程式架構/peer-discovery.md](../程式架構/peer-discovery.md) 同步。

### 2026-11-26 ─ 定稿先於公告、公告待送出由帳本重送（issue 001505、001515）

定稿原本先寫公告再推進邊界，兩者的先後使滿載狀態無法自行解除；邊界驗證也排在 latest 寫入之後。改為：
邊界唯讀驗證 → 存檔 → 推進紀錄連同公告待送出 → latest → 邊界 commit → 完成紀錄 → 寫公告 → 重建，公告寫入失敗不使定稿失敗。
control envelope 加第七欄 `announcementPending`（有界清單、至多 24 筆），帳本依清單由舊到新自行重送並依既有退避表重試，
衝突隔離期間不送；待送出的情形由 `getRecoveryStatus` 的 `pendingAnnouncement` 回報，簽署工具的 `/status` 同步顯示。每一輪
送出前先補做尚未完成的邊界推進；保留範圍內既有的公告要憑證有效才算已送出，驗證結果以條目為單位記住、每一輪新驗的量有上限；公告寫入成功而紀錄移除失敗時，同一執行期只重試移除、不再寫一則。採納端的邊界唯讀驗證同樣移到任何持久變更之前。既有本機 control 資料不遷移。改寫 `finalizeCheckpoint` 條、LEDGER-R-040、R-041、R-043、
R-076。

### 2026-11-26 ─ 切面容量被拒的定稿公告不落盤採納（issue 001505）

遠端送來的定稿公告只因本機切面容量（`cut-full`）被拒時，整批照舊不落盤，其中的公告交給帳本層送進同一個採納佇列；採納後邊界
推進、切面縮小，對方重送的條目照常落盤。因其他原因被拒的批次不交出。未落盤的公告不留下可供掃描的條目，被佇列擋下或採納
完成前重啟時要等對方再送。改寫 LEDGER-R-041、R-046。

### 2026-11-26 ─ ingest failure 期間照常採納與採納的背景重掃（issue 001510、001564）

ingest failure 期間到達的定稿公告原本不進採納流程；採納失敗的公告在同一執行期內也沒有再處理的機制。改為：
failure 期間公告照常進採納佇列，成功的全量重建把範圍內的公告送進佇列；落盤的公告重試用盡或因佇列容量被拒時，帳本依退避表
排背景重掃，不設啟動對帳的 pending、不影響業務讀寫。背景重掃不設總次數上限、不反映在復原狀態。改寫 LEDGER-R-041、R-048。

### 2026-11-26 ─ 以淘汰邊界開庫、衝突隔離的恢復方式為鏈重生（issue 001507）

衝突隔離把狀態基底退回共同 previous 後，重啟原本以它的 heads 開庫，而那些條目可能已被淘汰。改為以 control 的 `latest`
（最後一個已採納的檢查點，衝突隔離不後退）所指檢查點的 heads 開庫，狀態基底仍取 `effective`。衝突隔離沒有解除程序，恢復方式
是鏈重生，切點取共同 previous 或更早的良好檢查點；營運文件的 `conflict` 處置與資料系統第 19 節的適用情境同步補上。改寫
LEDGER-R-040、R-042、R-043、R-073。

### 2026-11-26 ─ 開庫時狀態塊取不到進入 recovery（issue 001526）

最新檢查點的狀態塊取不到時，`open` 原本整個失敗且不會自行重試。改為只有這一種初始重建失敗（固定代碼
`checkpoint-state-unavailable`）讓 `open` 回成功並進入 ingest recovery，依退避表向內容儲存重取；其他初始重建失敗照舊使
`open` 失敗。`open` 回成功不再代表業務狀態可讀。治理簽署工具在這種狀態下照常啟動、同步閘不通過；瀏覽器組裝目前仍以啟動失敗
處理（issue 001570）。改寫 LEDGER-R-048、R-078。

### 2026-11-26 ─ 採納時補通知與通知層事件鍵去重（issue 001561、001568、001552）

採納在 latest 寫入後中斷而由補做完成時，待通知的條目可能不再通知；ingest failure 期間到達、之後被採納的檢查點涵蓋的條目，
是否通知取決於採納與退避重試的先後；重新建立的事件會重複通知。改為：以檢查點為基底重建時，把採納當下重算驗過、被它涵蓋而
本 runtime 尚未通知過的條目列入待通知（開庫前的歷史不補發，只對完整重算的採納模式有效）；通知層以事件鍵辨認同一事件，
已由另一筆條目通知過就不再通知，事件鍵以兩個世代有界保存。採納當下驗過的涵蓋範圍至多保留 4 代，前一代的重建尚未成功就
採納下一代時一併補上；待通知超過本機條目數上限時，捨棄只靠涵蓋留著的條目。fold 層的短暫重複套用維持已知限制。改寫 LEDGER-R-049 與
「條目有效性的已知限制」。
[程式架構/ledger-checkpoint.md](../程式架構/ledger-checkpoint.md)、[程式架構/ledger.md](../程式架構/ledger.md) 同步。

### 2026-11-26 ─ 檢查點切面分業務上限與硬上限、控制事件保留額度（issue 001563）

切面滿載時檢查點控制事件與業務條目同樣被拒，節點無法自行恢復。新增業務上限
`LEDGER_CUT_BUSINESS_ENTRY_LIMIT`（9,000），硬上限維持 10,000：超過業務上限後只收保留批次（整批都是本代簽署者對目前錨寫的
提案或投票事件，且沒有相同事件內容的條目），容量拒絕以 `cut-full` 回報。檢查點控制事件的寫入不經 Admission outbox，提案寫入
失敗時不撤鎖、之後重送同一本體。這是第一段，保證一位簽署者時切面超過業務上限後仍可提案與定稿；三位以上簽署者的處理為
第二段（issue 001566）。改寫 LEDGER-R-039、R-045、R-103、R-108、R-109、R-077，新增 LEDGER-R-110。

### 2026-11-26 ─ 治理簽署者擴編改採候補方式（issue 001566、001539）

擴編步驟原本在寫入設定變更之後才部署新成員。改為候補方式：維持一位簽署者，候補者先產生金鑰、部署簽署工具並同步，以非簽署者
身分閒置；候補湊滿三位並完成上線確認後，由現任一次升到四位。三位時門檻為三、沒有離線容忍，四位才容得下一位離線；兩位不是
合法的名單大小。擴編前須完成 issue 001566，擴編後的設定變更需要多人收簽（issue 001539，尚未實作）。
