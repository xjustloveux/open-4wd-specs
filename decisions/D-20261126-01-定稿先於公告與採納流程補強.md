# D-20261126-01｜定稿先於公告與採納流程補強

## 背景與驅動力

定稿原本先把公告寫進帳本，再寫 latest 與推進邊界，兩者的先後使滿載狀態無法自行解除（issue 001505）。邊界的驗證排在 latest 寫入之後，檢查點 heads 不能成為本機邊界時會留下「latest 已設、
邊界未推進」的狀態（issue 001515）。以下幾項是同一段流程上的其他缺口：

- ingest failure 期間到達的定稿公告不進採納流程，而有些重建失敗只有採納新檢查點才會解除（issue 001510）；採納失敗的公告在
  同一執行期內沒有再處理的機制（issue 001564）。
- 衝突隔離把狀態基底退回共同 previous，重啟時 log 也以它的 heads 開庫，但那些條目可能已被淘汰（issue 001507）。
- 最新檢查點的狀態塊取不到時，開庫整個失敗且不會自行重試（issue 001526 第 2 項）。
- 採納在 latest 寫入之後中斷、由補做完成時，原本待通知的條目可能不再通知（issue 001561）；ingest failure 期間到達、之後被
  採納的檢查點涵蓋的條目，是否通知取決於採納與退避重試的先後（issue 001568）；被重新建立的事件會重複通知（issue 001552）。

專案在 pre_launch，沒有已發布的本機資料需要相容。

## 考慮過的選項

- 公告的處理（issue 001505）：(甲) 定稿先於公告、公告失敗由帳本重送；(乙) 為公告保留一段配額；(丙) 公告因容量被拒時不落盤
  也可採納；(丁) 依條目數提前觸發檢查點；(戊) 讓公告不計入儲存配額。採甲加丙，丁已先行落地；乙要在 log 層驗憑證並另設上限，
  戊在硬配額上多開一個例外，皆不採。
- 淘汰邊界的承載：另加一個持久欄位，或沿用 control 既有的 `latest` 欄。`latest` 只由採納與定稿前進、衝突隔離不使它後退，
  已具備所需性質，採後者，少一個要同步維護的欄位。
- 公告待送出的對外呈現：在復原狀態加選填欄位，或新增一個復原階段。待送出不影響業務讀寫，可與既有階段同時存在，採前者。
- 不落盤採納的適用範圍：只限切面容量拒絕，或任何落盤失敗都交出。後者會讓沒有通過切面判定的公告進入採納，不採。
- 開庫時初始重建失敗：只把「最新檢查點的狀態塊取不到」轉為開庫成功並進入 recovery，或所有失敗都轉。後者會讓本機資料不一致的
  節點無限重試而不報錯，採前者。
- 採納的再處理：只補上 ingest failure 期間照常採納，或另加背景重掃。只做前者時，採納失敗的公告在同一執行期內沒有再處理的
  機制（issue 001564），採後者。
- latest 寫入之後的失敗：維持 rollback 邊界並由推進紀錄補做，或改為不 rollback。不 rollback 會讓邊界先於待定稿索引的錨、
  保留判定依據與狀態基底前進，要消除不一致就得在失敗路徑也重建，採前者，定稿與採納兩端一致。
- 通知缺口（issue 001568）：採納時把被涵蓋而未通知的條目補上，或接受「被檢查點涵蓋的條目視為歷史」。採前者，使同一執行期內
  到達的事件在 LEDGER-R-049 所列限制內至少通知一次。
- 重複通知（issue 001552）：只在通知層以事件鍵去重，或另在 fold 內去重。後者等於新增一條共識規則、影響狀態 CID，而重複套用
  只存在於尚未採納該檢查點的節點、採納後收斂，採前者。

## 決定

- **定稿順序**：邊界唯讀驗證 → 內容塊、本體與憑證存檔 → 推進紀錄連同公告待送出（同一次 control CAS）→ latest → 邊界
  commit → 完成推進紀錄 → 寫公告 → 重建。公告寫入失敗不使定稿失敗。
- **公告待送出與重送**：control envelope 加一欄有界清單記錄尚未確認送出的本體；帳本依清單由舊到新自行重送，舊的送不出就停，
  依既有退避表重試；公告的寫入不受 ingest failure 與啟動對帳的業務閘限制，衝突隔離期間不送。待送出的情形經復原狀態的
  選填欄位對外回報。
- **不落盤採納**：遠端送來的定稿公告只因本機切面容量被拒時，不落盤也送進同一個採納佇列；其他原因被拒的不交出。
- **採納順序**：邊界唯讀驗證排在任何持久變更之前，兩種採納模式相同；latest 之後的失敗維持 rollback 並由推進紀錄補做。
- **ingest failure 期間照常採納**；成功的全量重建把範圍內的公告送進採納佇列。落盤的公告重試用盡或因佇列容量被拒時，
  帳本依退避排背景重掃，不設啟動對帳的 pending。
- **以淘汰邊界開庫**：log 以 control 的 `latest` 所指檢查點的 heads 開庫，狀態基底取 `effective`。衝突隔離沒有解除程序，
  恢復方式是鏈重生。
- **開庫時狀態塊取不到**：只有這一種初始重建失敗轉為開庫成功並進入 recovery，依退避重取；其他失敗照舊使開庫失敗。
- **採納時補通知**：以檢查點為基底重建時，把採納當下重算驗過、被它涵蓋而本 runtime 尚未通知過的條目列入待通知；開庫前的
  歷史不補發。只對完整重算的採納模式有效。
- **通知層事件鍵去重**：同一事件已由另一筆條目通知過時不再通知；已通知的事件鍵以兩個世代有界保存。fold 不去重。

現況規格：[ledger-checkpoint.md](../程式架構/ledger-checkpoint.md) 第 3、4 節（`finalizeCheckpoint` 條、LEDGER-R-040 至 R-043、
R-046、R-048、R-049）、[ledger.md](../程式架構/ledger.md) 第 10、11 節（LEDGER-R-073、R-076、R-078）、
[governance-signer.md](../程式架構/governance-signer.md)、[open-4wd-signer.md](../部署資訊/open-4wd-signer.md) 第 6.4 節、
[資料系統.md](../資料系統.md) 第 19 節。

## 後果與影響

- 不改事件格式、wire 與共識規則。control envelope 多一欄，是本機持久格式的變更；專案在 pre_launch，不遷移，既有的本機
  control 資料讀取時被拒，需清除後重來。
- 定稿或提案回成功代表本機已採納並推進邊界，公告可能尚未寫出。本機已定稿而公告未送出期間，其他節點要等公告補送才會採納。
- `open` 回成功不再代表業務狀態可讀，呼叫端須看復原狀態。瀏覽器組裝目前在開庫成功但仍在 recovery 時仍以啟動失敗處理，
  治理簽署工具照常啟動（issue 001570）。正式的內容儲存埠把底層讀取錯誤也回報為取不到，本機內容儲存損毀時節點會停在 recovery
  而不是開庫失敗（issue 001571）。最新檢查點的狀態塊一直取不到時節點停在 recovery，由較新的檢查點重新啟動的入口尚未提供
  （issue 001527）。
- 未落盤的公告不留下可供啟動掃描或背景重掃讀取的條目：被採納佇列擋下、或採納完成前重啟時即丟棄，要等對方再送。集合分歧
  （檢查點 heads 含本機沒有的條目）不在本決策範圍（issue 001512）。
- 待送出清單中某一筆的憑證在本機取不到時，重送停在那一筆，沒有自動放棄或人工移除的入口（issue 001567）。
- 背景重掃不設總次數上限，一直無法採納的落盤公告會讓重掃以最長間隔持續到它離開本機保留範圍（issue 001564）；背景重掃不反映
  在復原狀態。
- 通知的已知限制：事件鍵移出之後、重啟之後、或基線內事件的另一筆條目到達時，同一事件會再通知一次；曾通知而後不再被接受的
  條目被檢查點涵蓋時，事件鍵已移出就會再通知一次；跨次送出不保證等於帳本順序；採納當下驗過的涵蓋範圍至多保留 4 代，連續採納
  超過 4 代而其間沒有任何一次重建成功時，被捨棄各代涵蓋而未通知的條目不補通知；待通知超過本機條目數上限時，由最早列入的開始
  捨棄已不在已接受集合、只靠涵蓋留著的條目，不補通知。訂閱者仍須冪等。fold 在尚未採納該檢查點的
  節點上短暫重複套用同一事件，維持已知限制（issue 001552、issue 001573；以條目 CID
  作引用的紀錄可能指向已成孤兒的舊條目，issue 001572）。
- pinning 節點 vendored 的帳本與其組裝層須同步這些改動（issue 001488）。
- 修訂 [D-20261123-03](D-20261123-03-帳本讀取以本機保留範圍為界.md)：重啟時 log 的邊界改以 control 的 `latest` 重建，衝突隔離後
  與 `effective` 不同；找既有公告的範圍改為本機保留範圍，讀取失敗時公告留在待送出清單、定稿結果不變；未落盤的公告可進採納而
  不在掃描範圍內；開庫時狀態塊讀不到改為開庫成功並進入 recovery。修訂
  [D-20261123-04](D-20261123-04-帳本recovery失敗後依退避重試.md)：ingest failure 期間公告不進採納流程的缺口已補；退避表多了
  定稿公告重送與採納背景重掃兩個使用者；復原狀態新增公告待送出的選填欄位。修訂
  [D-20261124-04](D-20261124-04-條目有效性以檢查點切面與確定性時鐘判定.md) 後果段：重新建立的事件造成的重複通知，改由通知層
  事件鍵去重處理。

## 定案紀錄

2026-11-26 由使用者裁決：公告處理採定稿先於公告加不落盤採納（只限容量拒絕）；淘汰邊界沿用 `latest` 欄；公告待送出以復原狀態的
選填欄位呈現、清單有界並由舊到新重送；只有狀態塊取不到才轉為開庫成功進入 recovery；加背景重掃；採納時補通知；重複通知只做
通知層事件鍵去重；恢復程序寫入營運文件與資料系統第 19 節；既有本機資料不遷移。
