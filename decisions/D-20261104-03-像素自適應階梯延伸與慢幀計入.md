# D-20261104-03｜像素自適應階梯延伸與慢幀計入

## 背景與驅動力

issue 001284：公版程序化交付後 canonical-smoke 首次在 PR 路徑真跑，GitHub runner 以 SwiftShader 軟體 GL
跑比賽場景只有約 0.5 fps（trace screencast 幀距中位 1.82 秒）。[D-20261102-02](D-20261102-02-比賽視口背景層移除與像素自適應.md)
的自適應倍率把「間隔達 500 ms」當成暫停（背景分頁 rAF 1 Hz、視窗被遮）而不計樣本，於是每幀數秒的環境永遠
不降階，比賽維持 100% 倍率；階梯最低 45 也是為內顯機器選的，沒有為無 GPU 的環境留餘地。e2e 的
`expectCanonicalRaceRendered` 以 Playwright 元素截圖取樣 canvas，在這種環境單次超過 48 秒、60 秒 poll 容不下一次。

## 考慮過的選項

- 只改測試（放寬 poll、縮圖取樣）：比賽端仍以 0.5 fps 畫全尺寸，取樣成本只是變得剛好過關，真實的無 GPU 或
  極低階裝置仍不會降階。
- 只改比賽端：取樣成本仍是全尺寸讀回，CI 一輪 40 分鐘才知道夠不夠。
- 兩者都做（採納）：比賽端對災難性慢幀也降階並把階梯延伸到 30／20；測試端改用 CDP 0.1 倍縮圖取樣、poll 放寬到 180 秒
  並把最後一次取樣值寫進失敗訊息。
- 另看過關閉 outline 後處理：目前主題沒有啟用 outline（[D-20261102-01](D-20261102-01-比賽視口固定算圖削減.md)
  已述），不是槓桿，不列入。

## 決定

1. `ADAPTIVE_RENDER_SCALE_LADDER` 延伸為 `[100, 80, 60, 45, 30, 20]`：45 以下兩階只有在 45 仍持續超過兩幀預算時才會走到；
   判定參數（2 秒窗 P90、降階 2 倍持續 2 秒、升階 0.8 倍持續 10 秒、靜置 2 秒）不變。
2. `maxSampleMs`（500）的語意由「視為暫停、不計樣本」改為「單一間隔計入的上限」：更長的間隔以 500 ms 計入窗內，
   災難性慢幀因此是過載訊號、會逐階降到底；背景分頁的 rAF 節流由 viewport 既有的 `document.hidden` 不餵樣本處理，
   回到前景後跨越暫停的第一個間隔只算一個樣本、撐不起 2 秒持續，不會誤降階。
3. e2e helper `expectCanonicalRaceRendered`：Chromium 以 CDP `Page.captureScreenshot` 對 canvas 範圍取 0.1 倍 jpeg
   後在頁內解碼取樣（判定門檻不變），其他瀏覽器維持元素截圖；poll 時限 60→180 秒，失敗訊息附最後一次取樣值。
4. 守門：`adaptive-render-scale.spec` 改為階梯六階、持續過載逐階降到 20、災難性慢幀（1.8 秒間隔）逐階降到底、
   回前景跨越暫停的單一長間隔不降階；`race-render-budget.spec` 的階梯全枚舉自動涵蓋新階。

## 後果與影響

- 無 GPU 或極低階環境的比賽畫面會降到 20%（1280×720 視口＝256×144），畫質明顯下降但保住幀率；內顯與高階機
  的行為不變（45 已夠的環境不會再往下）。
- 效能警告橫幅語意不變（降階中即顯示）。倍率仍只在 session 內生效、不進 SavedState 或 replay hash。
- 現況規格：[程式架構/ui-frontend.md](../程式架構/ui-frontend.md) renderer／context 預算段、
  [程式架構/settings.md](../程式架構/settings.md) 的 drawing-buffer ratio 說明。
