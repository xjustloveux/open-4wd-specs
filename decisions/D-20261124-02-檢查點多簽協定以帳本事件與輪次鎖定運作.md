# D-20261124-02｜檢查點多簽協定以帳本事件與輪次鎖定運作

## 背景與驅動力

規格沒有定義檢查點提案與簽章怎麼傳遞，只有提案物件與 30 分鐘有效期；也沒有任何執行者會在固定時間提案
（issue 001535、001538）。既有先例中，結算多簽依賴同時在線的 DataChannel，仲裁 attestation 以帳本事件收集
（[D-20261122-07](D-20261122-07-仲裁attestation以帳本事件收集.md)）。檢查點需要在簽署者不同時在線時運作，並在
工具重啟或遷移後不遺忘自己簽過什麼。另外，提案者原本以當下時鐘折疊狀態、之後才另取時間當本體 timestamp，
覆核者則以本體 timestamp 折疊，時戳落在兩者之間的條目會使雙方算出不同狀態；提案又受 `deriveStateAt` 的
10 秒總時限限制（issue 001534）。

## 考慮過的選項

- gossip 主題傳遞提案與簽章：不持久、要求同時在線、簽章歷史無法由共享資料推回，不採納。
- 帳本事件加簡單鎖定與重提案（採納）。
- 帳本事件加完整 BFT 輪次切換（鎖定與解鎖證明）：可自動解除分裂，但協定與測試成本高很多；以 24 小時的節奏
  與預期 1 到 7 位簽署者，保留為日後升級方向（本體帶 `round` 已為此預留）。

## 決定

- 新增 `ledger-checkpoint-proposal`（指定提案者提出本體與自己的一票）與 `ledger-checkpoint-signature`（前代 signer
  的一票）兩種單簽帳本事件。三種檢查點控制事件不進業務 fold；每個節點以最新已採納檢查點為錨，從帳本確定性地
  推出待定稿索引（不進 `DerivedState`）。非成員事件可通過准入，但不採計。符合條件的提案全部保留、投給它們的票
  全部記錄；候選本體為每位提案者在此錨 canonical 順序最前的本體，加上任何簽署者以其在此錨 canonical 順序第一張
  票投給的本體（升格，升格前已收的票一併計入）。提案者自己的票不使自己的其他本體升格，第二張以後的票也不升格，
  候選本體數因此不超過 2N − 1（N 為前代 signer set 大小），索引不設過期；同一提案者的第二份簽章即使其本體升格仍記為重複簽署證據。投票對象、
  可定稿與卡死只看候選本體。任何節點見某候選本體已有至少 quorum 票即可組憑證定稿，不需要治理金鑰。
- 輪次每輪 30 分鐘（`CHECKPOINT_ROUND_TIMEOUT_MS`，由 `CHECKPOINT_PROPOSAL_EXPIRY_MS` 改名），起點為前一檢查點
  timestamp（創世時為創世狀態的 `derivedAt`）；每輪的指定提案者為前代 signer set（canonical 序）中第 (H + 輪次) mod N
  位，H 取鏈身分 chainId 與 previous 的雜湊，輪次本身不進雜湊。
- 一位 signer 對同一 previous 只投一個本體，不論輪次；投票順序固定為寫本機鎖定 → 簽 → 寫入事件，受約束的本體為
  本機鎖定紀錄與帳本上自己的票的聯集；缺鎖定紀錄時提案、投票與釋放都拒絕。
- 重提案：待定稿索引有候選本體時，提案先回到候選本體。已鎖定的 signer 不投新票；未鎖定時依票數降序、同票本體 CID
  升序逐一以與投票相同的覆核重算，投給第一個通過者。沒有本體通過覆核時，才由本輪指定提案者產生新本體（其餘
  signer 回 `not-designated`）；已在此錨提出過本體的 signer 不再提出第二個。
- 誠實簽署者分裂到任一本體都不可能達 quorum 時判定卡死；卡死起點取由帳本推出、使條件最近一次成立的那筆投票
  timestamp。卡死持續至少 24 小時後，signer 才可由人工以逐字確認字串釋放自己的鎖定，改投
  全網一致的投票對象（得票最多、同票取本體 CID 較小者）；只有綁在其他本體的 signer 可以釋放，每個 previous 每人
  一次，只改本機鎖定紀錄。
- 索引中自己對同一錨投過兩個以上未釋放的本體時（同一金鑰在別處運作），提案與投票一律拒絕；定稿不因此阻擋。
- 觸發為距前一檢查點 24 小時，或前一檢查點之後累積 6,000 筆條目且距前一檢查點至少 60 分鐘；首個檢查點不受間隔
  限制。條目數含無法解碼與控制事件，由 DAG 決定，提案、覆核與完整重算採納共用同一段候選折疊。
- 提案先定本體 timestamp，再以與覆核相同的候選折疊成形狀態，不套 `deriveStateAt` 的總時限。
- 覆核只要求本體 timestamp 不晚於本機時鐘加 30 秒，不設下限。
- `config-update` 的多人收簽沿用同一模式（`config-update-proposal` 與 `config-update-signature` 帳本事件、每位
  signer 對同一個前一 epoch 只簽一份、一律手動提出、提案期 7 天），分段實作：N=1 的手動指令隨 issue 001535，
  提案與簽章事件、多人收簽在擴編到 N≥3 前隨 issue 001539 落地；`config-update` 的規格條文屆時才修改。
- 與原設計的兩項出入：遠端採納（`full-refold` 與 `quorum-follow`）不檢查本體提案者是否為該輪指定提案者，
  安全由憑證的 quorum 保證（作惡者少於三分之一時，quorum 中至少一位誠實 signer 在簽署前覆核過）；`full-refold`
  另做完整重算，`quorum-follow` 不重算。設計中的待定稿表會清除過期項目，實作改為不設過期、以候選本體的定義
  限制候選數，換錨時整體重建。

## 後果與影響

- 每次檢查點多寫約 N 筆條目並付工作量證明；以 24 小時的節奏可以忽略。簽章歷史可由帳本推出，重啟或遷移後不會
  遺忘鎖定。
- 作惡者少於三分之一時不會出現兩個可定稿的不同本體；分裂需要人工處理，釋放鎖定本質上是受控的重複簽署。
- 落地後的獨立驗證發現三處規則缺陷並已修正：既有本體路徑原本只投得票最多者且覆核不過即停止、索引另以每錨本體數
  上限收錄，覆核不過的本體可能使檢查點無法推進；人工釋放原本允許改投 from 以外得票最多者，平票時兩側可同時改投
  而各自達到 quorum；索引一度改為每位提案者只收錄 canonical 順序最前的本體，同一提案者在不同分支各有本體時，
  合併後較晚本體與其票被丟棄，投過它的簽署者仍被鎖定卻被算成未投票，檢查點可能既無法推進也不判為卡死。修正後的
  規則即本決定的重提案、候選本體（含升格）與釋放三條。
- 檢查點 API 改為以本體 CID 操作（提案、投票、定稿、待定稿檢視、輪次資訊、人工釋放），失敗以帶 code 的錯誤
  回報；其中缺鎖定紀錄、治理狀態或重算基底不可得、本體或簽章無效、釋放條件不符四種是實作時補上的。完整清單見 [程式架構/interfaces.md](../程式架構/interfaces.md)。
- 瀏覽器不自動簽署；執行提案與投票的常駐簽署工具另行決策（issue 001535）。
