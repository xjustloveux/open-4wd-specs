# D-20261113-10｜開賽巡禮鏡位規劃移出呈現就緒路徑

## 背景與驅動力

[D-20261113-03](D-20261113-03-開賽巡禮依場地挑選鏡位.md) 讓 viewport 在場地載入後依場地資料規劃三個巡禮鏡位。
規劃對場地發最多 900 條射線，走的是 three.js 原生 raycaster、沒有加速結構，公版場地約 44,000 個三角形。
這段計算原本接在場地載入之後、首幀 render 之前，落在「等待呈現就緒」的時間預算內。

issue 001363：本機測試等呈現就緒的上限是 `RACE_READY_STALL_TIMEOUT_MS`（30 秒），逾時就照常開賽。CI 上這一批把
開賽載入時間推到該上限附近：同一份程式在 PR 的執行量到遮罩到倒數 30,997 毫秒、在 master 量到 37,345 毫秒
（上限 36,000，含固定 6 秒巡禮），後者等於就緒等待逾時。改動前的量測是 16,362 毫秒。

本機以 4 倍 CPU 節流重現同一個案例：基準 21.3 到 22.7 秒；把鏡位規劃的射線預算設為 0 則為 18.2 秒；
CPU profile 的前 20 名幾乎全是 three.js 射線檢測的內部函式。

## 考慮過的選項

- **維持現況、放寬等待上限**：把「載入要多久才算異常」的門檻調高來掩蓋變慢，等待上限本身的意義變模糊，否決。
- **縮小射線預算**：成本線性下降，但鏡位品質隨之下降，而且門檻仍然在就緒路徑上，場地更大時會再次逼近，否決。
- **規劃移到首幀 render 之後**（採納）：就緒只等場地、車輛與首幀，規劃改在首幀之後排程。

## 決定

- viewport 在場地套用時只登記待規劃的場地，不做規劃；首幀 render 完成（呈現就緒已可成立）之後才排程規劃。
- 規劃完成前巡禮由車群導播代打——這是既有的退路：鏡位尚未規劃時，巡禮模式本來就改用車群導播。
- 場地已換掉或元件已銷毀時放棄該次規劃。

## 後果與影響

- 等待呈現就緒的時間不再包含鏡位規劃。本機以 4 倍 CPU 節流量測同一個案例：遮罩到倒數由 21.3 到 22.7 秒
  降為 16.2 秒。CI 上的實際改善沒有量測。
- 規劃本身的成本沒有消失，只是移到首幀之後；對使用者而言落在開賽巡禮的前段，規劃完成前的鏡頭由車群導播掌鏡。
- 現況規格：[流程/比賽進行.md](../流程/比賽進行.md)「開賽巡禮」段。
- 與既有決策的關係：amends [D-20261113-03](D-20261113-03-開賽巡禮依場地挑選鏡位.md) 中「場地載入後規劃」的時機。

## 定案紀錄

2026-11-13 查明 CI 失敗來自開賽載入時間逼近就緒等待上限，並以對照量測確認鏡位規劃是最大的單一來源；
使用者在「移出就緒路徑」與「降低射線預算」之間裁決採前者。
