# D-20261112-02｜BGM 改以 Web Audio buffer 循環播放

## 背景與驅動力

issue 001315：BGM 通道原本是媒體元素加 `loop`。主題音訊的七首 BGM 都做成無縫循環，使用者也特別要求循環首尾
不能突兀。在 Chromium 以媒體元素循環 `default` 的首頁曲並擷取輸出，以檔尾前 0.3、0.6、1.0、2.0 秒四個位置為錨點
比對解碼結果，四個錨點都量到檔尾與檔頭之間多出 6.5 毫秒，其中一個 5 毫秒視窗完全靜音。同一個檔以
`decodeAudioData` 解碼，取樣數與來源相同，首尾連續。問題在播放方式，不在音檔。

另一個疑慮是快取：媒體元素以 Range 請求取檔，開發伺服器回應 206；service worker 的 `cacheFirst` 只把狀態 200 的
回應寫入快取。[D-20261112-01](D-20261112-01-主題音訊採程式合成與預載分層.md) 決定 BGM 不列入 install precache 之後，
BGM 要靠播放時的取檔進快取才能離線播放。

## 考慮過的選項

- **維持媒體元素循環**：串流播放、記憶體用量小；接點有靜音，取檔回應進不了快取。
- **兩個媒體元素交接**：仍是串流，但媒體元素的起播時間無法精確到取樣，音檔的餘音已回捲到檔頭，交接點差幾毫秒
  就會聽到重疊或缺口。
- **取整檔解碼後以 `AudioBufferSourceNode` 循環**：接點由 buffer 首尾取樣決定；`fetch` 的回應是 200。代價是播放中
  的每首曲子佔用解碼後的 PCM，48 kHz 立體聲每分鐘約 23 MB，最長的三分鐘曲目約 69 MB，轉場重疊時兩首同時存在，連續快速換曲時尚未結束的載入還會讓解碼結果短暫多於兩首；
  曲子要等整檔下載並解碼完才開始。

## 決定

BGM 改為取整檔、`decodeAudioData` 解碼後以 `AudioBufferSourceNode` 循環播放。

- BGM 使用自己的 `AudioContext`，要求 48 kHz（與音檔相同，解碼不重新取樣）；平台不接受時改用裝置預設取樣率。
- 通道不保留解碼快取；淡出收口即停止並釋放 buffer。
- 新曲取檔與解碼完成、開始播放後才淡入；前曲在這段期間照常淡出。
- 取檔或解碼失敗時收回通道並退回未解鎖狀態，下一次使用者手勢再試；在那之前，頁面回到前景不會恢復各 context。
- 使用者手勢與頁面回到前景時恢復 BGM 的 context，不重建也不重播曲目。

## 後果與影響

- 修改後在 Chromium 攔截 App 自己建立的循環音源（月兔主題首頁曲，4189091 個取樣），從檔尾前 3 秒起播，在音量控制之前
  擷取訊號：四個錨點量到的多餘取樣都是 0，接點前後各 0.1 秒與解碼結果逐取樣相同。只量了這一首、這一種瀏覽器。
- App 的 BGM 請求在開發伺服器上由 206 變為 200。依 `cacheFirst` 的規則這個回應會寫入快取；正式建置下的離線播放
  還沒有實測。
- 換曲時前曲淡出與新曲淡入之間，可能出現等同下載加解碼時間的空檔；量測空檔長度不在本次範圍。
- 記憶體用量如上，行動裝置上的實際影響沒有量測。
- 現況規格：[程式架構/audio-system.md](../程式架構/audio-system.md) 第 4 節。
- 與既有決策的關係：amends [D-20261112-01](D-20261112-01-主題音訊採程式合成與預載分層.md) 後果中「BGM 目前以媒體元素播放」
  的敘述。

## 定案紀錄

2026-11-12 把主題音訊換進專案後實測發現媒體元素的循環接點有靜音，登錄為 issue 001315 並說明修正需要改播放方式、
會增加記憶體用量。使用者指示先處理這一項。
