# D-20261124-06｜定稿與採納後的重建失敗計入退避

## 背景與驅動力

[D-20261123-04](D-20261123-04-帳本recovery失敗後依退避重試.md) 決定段第一條末句分號後的部分寫明「checkpoint 採納或定稿後的
重建是另一個佇列工作，不經 single-flight，失敗不計入退避」。實際上這兩處的失敗被吞掉了：定稿回成功、復原狀態維持 idle、不排重試，節點繼續
提供檢查點之前的狀態；採納後的重建失敗讓該次採納回到重試，下一輪因 latest 已是該 checkpoint 直接視為已採納，
同樣不再重建（issue 001526）。定稿者手上沒有新檢查點的狀態塊、而內容儲存一時取不到時就會發生。

## 考慮過的選項

- **重建失敗時標記 ingest failure 並依既有退避表重試（採用）**：沿用已有的復原狀態與退避機制，原因消失後自動
  恢復；定稿與採納的結果不受影響。
- **維持現狀，等下一次明確同步重建**：明確同步沒有正式呼叫端，節點會一直停在檢查點之前。不採用。

## 決定

- checkpoint 定稿或採納後的重建失敗時，定稿或採納的結果不變（checkpoint 已提交），在同一個 state 佇列工作內
  標記 ingest failure，之後依 D-20261123-04 的退避表排下一次重試並計入失敗次數；已有待執行的重試時不改變它、
  也不計入。
- 採納路徑的重建不再於邊界 commit 之後失敗時回滾邊界。

本決策修訂 D-20261123-04 決定段第一條末句分號後的部分「checkpoint 採納或定稿後的重建是另一個佇列工作，不經
single-flight，失敗不計入退避」中失敗不計入退避的部分；該重建仍是另一個佇列工作、不經 single-flight，
其餘不變。

## 後果與影響

- 定稿或採納後重建失敗期間，業務讀寫依 ingest failure 一律 fail-closed，不再提供檢查點之前的狀態。
- 最新檢查點的狀態塊在開庫時取不到的行為不在本決策範圍（issue 001526 第二項，另行處理）。
- 現況規格：[ledger-checkpoint.md](../程式架構/ledger-checkpoint.md) LEDGER-R-048。

## 定案紀錄

2026-11-24 由使用者裁決 issue 001526 第一項：定稿後重建失敗標為 ingest failure 並依退避重試。
