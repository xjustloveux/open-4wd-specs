# D-20261114-07｜節點 matrix 各軸縮放的允許範圍

## 背景與驅動力

[D-20261114-06](D-20261114-06-節點變換不合glTF規定時拒收.md) 拒收帶剪切的節點 `matrix`。issue 001396：
三個基底欄互相正交的 `matrix` 能通過那條檢核，但量級極端時編輯器仍無法正確分解。three.js 分解 `matrix`
時先算行列式，算出來是 0 就回傳單位旋轉與單位縮放；比賽端直接以宣告的矩陣相乘。實測三種情形兩邊不同：
三軸縮放都在 1e-108 以下（行列式下溢成 0）、基底欄長度在 1e155 以上（欄長平方溢位，畫面位置算成 NaN）、
有一欄全為零（掛在底下的路線點在畫面與比賽相差 1 公尺）。同樣的三組輸入把 `matrix` 換成 `scale` 欄位
宣告時不經過分解，實測兩邊一致。

## 考慮過的選項

- **`matrix` 各軸縮放限制在明確的範圍內**（採納）：規則容易說明，一次涵蓋三種情形。
- **只拒收行列式為 0 或非有限的 `matrix`**：規則較窄，但判斷取決於行列式的浮點結果，邊界不直觀。
- **`scale` 欄位套用同樣的範圍**：同一個變換不論怎麼宣告結果都相同。使用者原本裁決採用，條件是先確認
  沒有合法用途；動工後發現有（見定案紀錄），因此不採用。
- **不處理，記為已知限制**：作者把空節點的父層某軸壓成 0 時，畫面與比賽的位置不同而不自知。

## 決定

- 節點 `matrix` 的三個基底欄長度都必須在 1e-6 到 1e6 之間（兩端皆含），範圍外拒收；有一欄全為零的
  `matrix` 因此拒收。
- 以 `scale` 欄位宣告的節點不檢查量級，某軸為 0 也照常解析。
- 檢核與 D-20261114-06 寫在同一處，解析 scene graph 時逐節點執行。

## 後果與影響

- 同一個極端縮放以 `matrix` 宣告會被拒收、以 `scale` 宣告會被接受。兩者的差別在於 `matrix` 要經過
  編輯器分解，`scale` 不必。
- 以 `scale` 宣告、縮放退化的空節點仍由既有的驗證規則處理，例如路線點的世界座標框退化時回報
  `route-point-frame-invalid`；重生點的 `scale` 沒有語意，某軸為 0 時仍取它有效的前向。
- 動工前掃過的現有素材，節點各軸縮放（`matrix` 基底欄長度與 `scale` 分量的絕對值合計）落在 0.005 到 11
  之間，沒有為 0 的：本機測試素材夾 5142 個可讀的 GLB、主 repo 142 個、specs 108 個。
- 範圍限制的是單一節點自身的 `matrix`；多層節點相乘後的世界縮放不另外限制。
- 兩端皆含指的是算出來的欄長：單精度的 1e-6 實際是 9.99999997e-7，會被拒；旋轉後縮放恰在邊界的
  `matrix` 也可能因捨入被拒。離邊界百萬分之一以上實測沒有被拒。
- 現況規格：[建模參數/零件與共用介面.md](../建模參數/零件與共用介面.md) 第 2 節、
  [流程/UGC上傳.md](../流程/UGC上傳.md) 第 3 節。

## 定案紀錄

2026-11-14 使用者裁決 `matrix` 各軸縮放限制在明確範圍內，並同意 `scale` 欄位套用同樣的範圍，前提是先確認
現有內容沒有合法用途。實作後三個既有測試失敗，顯示現行設計容許以 `scale` 宣告、某軸為 0 的空節點：路線點
退化時由驗證規則以帶節點定位的結果回報，重生點的 `scale` 沒有語意。前提不成立，`scale` 欄位不套用範圍；使用者於同日確認。
